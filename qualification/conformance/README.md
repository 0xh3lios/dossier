# Specification and agent conformance

This layer tests the portable contracts in `spec/`. Run `npm run test:spec` for link discovery, a complete prose example, a semantic mutation, read-only verification, repeated integrity failures, an independent XState model of one cell's answers compared with the real publication rule and cell derivation, each evidence rule with its refusal, superseded answers, the owed second read, and the tripwire and flag names the spec and the code share. Run `npm run test:process` for XState paths that execute Dossier's actual CLI commands.

`qualification/tests/spec-lifecycle.test.ts` states that model from `spec/evidence.md`. One system cell has three questions, two TLC configurations and an inductive Apalache call, and HEAD keeps one answer to each. Its events are validated observations handed to the runner, a rerun at a new reach, edits that move the basis, and the owner's risk and forget. The model says which observation is published, kept or refused (ANSWER-SAME, ANSWER-REPLACE, ANSWER-VIOLATION, ANSWER-ABORTED), which answers a publication removes because the answers that decide stand in for them (ANSWER-SUPERSEDED), which answer decides the mark, the strongest of the current ones and the latest among equals, so that a check run after a proof goes and the proof stays, and when an acceptance holds: never past a new answer to the cell, from its own question or another. The test reaches each of its 719 states by a shortest path and sends every event from each. Each observation goes through the production rule and each mark through production's reading of the entries. It does not prove solver soundness, all possible histories, miscall classification, publication recovery or agent compliance. Existing checker/runner suites own parsing and execution validation, and `answers.test.ts` owns each rule's refusal.

`command-lifecycle.ts` supplies a separate model for real command sequences. Four generated paths cover its twelve declared events: author/check, abort/retry, edit/lapse/refresh, interrupted answer and decision publication, recovery, read and render. The adapter runs the CLI in temporary repositories, kills publishers at selected commit boundaries, then compares actual marks, owner authority and integrity findings with independently stated expectations. Read-only checks compare bytes, permissions and mtimes; a read changes no entry. A wrong recovery confirmation must grant no owner authority. No XState workflow state is persisted in a dossier or used by production code.

Additional risk paths run real decisions on a copy of Harbor, whose Control ships an accepted violation, and real TLC violation, accept, rerun, rerun at a new reach, edit, member change and refresh commands on a fresh system. They assert that accepting risk leaves the property violated, that a rerun giving the same answer writes nothing and keeps the acceptance, and that a new answer invalidates the old acceptance: one at a new reach, or one after the property's meaning, the scenario under the same name or a member changed. Set `JAVA` and `TLA_TOOLS` to run the live TLC path; otherwise that test explicitly skips. Set `DOSSIER_QUAL_KEEP=1` to retain command artifacts, whose paths appear in test diagnostics. These representative paths do not cover every possible history, concurrent interleaving or crash boundary. The integrity, initialization and trial-publication suites provide additional fault and concurrency checks.

`fixtures/budget.md` is a complete synthetic component. It keeps two independent limits so a missing capacity guard produces a refusal, walk or range failure. Its expected behavior is specified independently of the chart renderer. It carries no deployment assertion.

`fixtures/retired-actor-kind.md` is an expected refusal for the retired actor kind `contract`. Choosing a current actor kind requires understanding whether the sender is a modeled component or an external actor. `fixtures/snapshot-without-module.json` is an older dependency snapshot that lacks the generated module's identity. An entry resting on it is malformed, `answer malformed`, and lapse read against it still reports the generated module as moved: neither fills in the missing evidence. These small cases came from a real-project upgrade exercise.

## Agent exercises

Prepare each run before dispatch with `node qualification/conformance/prepare-agent.ts <exercise> <new-evaluation-directory>`, choosing an exercise from the table below. Give a fresh agent only that directory's `request.md`. It names a frozen plugin snapshot and an isolated writable workspace. A separate evaluator directory contains the grading code and points its production imports at the frozen plugin. The manifest retains the prompt hash, spec/plugin/evaluator fingerprints, preparation Node version, dependency lockfile identity and initial artifact inventory. Dependencies are shared from the installed plugin and identified by the lockfile; this is not a hermetic runtime image. The snapshot and raw workspace omit golden marks and grader code. Keep the evaluation directory outside the portable fixture.

| Exercise | Raw task and required work | Protected distinctions | Runtime |
| --- | --- | --- | --- |
| `budget` | Author a component from a payment question, record a chart trial and answer the question | Positive evidence versus blunders; finite checks versus proof; no invented owner acceptance | Node and XState |
| `compose-probe` | Compose supplied Source/Sink components, check a system equality and witness a scoped third-send question | Simultaneous wired effects and carried fields; refusals; unchanged member inputs; meaningful sensitivity evidence | Node and TLC |
| `refresh-decision` | Resume a prepared call after N1 changed, refresh only its scenarios and record exact supplied risk words | Stale evidence and stale acceptance; an unexpected result; no semantic weakening; accepted violation remains violated; unrelated cells stay stale | Node and TLC |
| `review` | Independently audit Control and a proposed publication claim, writing one report | Bounded versus proved; accepted violations; trace versus interpretation; read-only existing records | Node |

Grading of the two workflow exercises lets `dossier trial` publish: entries in the target system's `evidence/`, the readings beside them, `integrity.json`, and the bundles the runner leaves in the local `trials/`, which are no record. It requires the root marker, the existing authored inputs and the decision prefixes to stay as they were. A starting entry changes only when a trial of the exercise replaces its answer, and a starting answer that no trial replaced keeps its reading byte for byte. Preparation keeps the starting entries' text in the manifest, so the grader tells a fresh trial from an old one. Each cited trial is graded against the entry it established. The refresh exercise deliberately starts with a wrong, unexecuted prediction. Consuming that call into a new trial demonstrates continuation; it is not a process-crash or publication-recovery test. Those belong to the storage suites. Refreshing N1 under executor-offline asks the prepared call's question again, so its answer replaces the classified miscall, which the entry keeps as its previous answer. HEAD keeps no call for a replaced answer. The grader reads the prepared call's trial from its local bundle, bound by the bundle digest in that previous answer, so grade the exercise on the machine that ran it.

After completion, run `node qualification/conformance/grade-exercise.ts <evaluation-directory>` and save its stdout beside the manifest. It refuses a changed prompt, plugin or evaluator, then runs the frozen evaluator with the frozen production semantics. Its result identifies the evaluator and actual grading Node version separately from the preparation version. Later changes to the working checkout cannot silently change an old exercise's grading rules. When the graders, the requests or a contract they grade change, prepare each exercise again in a new directory. An earlier evaluation directory keeps grading by the evaluator and plugin it froze, and its result describes that snapshot only. Read the human explanations before recording an exercise as passing. A grading failure stays with the evaluation directory it came from, unchanged, and a retry uses a new one. The grader refuses an evaluation directory whose manifest does not identify a frozen evaluator. Keep that directory's result as it was, and prepare a new exercise instead of regrading it.

`agents/budget-request.md` is a task prompt. Supply a fresh agent the prompt, a clean writable temporary repository and the plugin path. Do not provide the fixture or expected answer. The agent must discover the contracts through the skill and produce actual artifacts. Grade the output with `node qualification/conformance/grade-agent.ts <workspace>`.

Record the agent task identifier, spec version or content hash, workspace, command results and grader output in the development work note. Keep temporary agent logs and answers out of the portable fixture. A test of the grader is not an agent run; a fresh-agent exercise is not a live test of a host's permissions.

Before preparing `compose-probe` or `refresh-decision`, set the existing `JAVA` and `TLA_TOOLS` environment. Preparation embeds their resolved paths and execution instructions in the frozen local request, and their file hashes and environment values in the manifest. It also identifies the preparation Node executable; grading records its own Node executable and hash. Preparation never installs or runs a solver. When the toolchain is absent, the evaluation directory says it supports preparation checks only; prepare a new one with the toolchain before live dispatch. These machine-specific paths stay in local evaluation records, outside the portable prompts and fixtures.

Solvers and the rest of the JDK remain shared, like `node_modules`. The hashes identify preparation inputs; they are not a frozen runtime image or an attestation that an agent used those exact binaries. Published answers record their observed checker versions. Grading reads the entries without requiring or rerunning the solver. `qualification/tests/agent-workflows.test.ts` tests raw preparation without a solver and exercises both complete transformations through real TLC when `TLA_TOOLS` is provided. A skipped solver test leaves that demonstration unverified. In hosts that restrict loopback sockets, TLC may need the host's normal sandbox approval because its local worker binds a port.

The grader independently replays the raw budget task and checks its published answer and owner boundary. The cited trial must have established the current answer of an ordinary passing chart question that covers the requested walk; a successful sensitivity blunder is negative evidence and cannot fill that role. Negative tests edit the published entry, promote a chart result to proof, insert an unauthorized owner decision and substitute a real blunder trial. Altering or deleting the local bundle changes no grade. The free-text explanation still needs review; a nonempty limitations array cannot establish that every claim is sound.

`agents/review-request.md` uses a clean copy of Harbor and one review report. Before dispatch, save `node qualification/conformance/files.ts <workspace>` to an evaluator-owned file outside that workspace. After the agent finishes, run `node qualification/conformance/grade-review.ts <workspace> <before.json> <report-relative-path>`. It checks the nine cell claims, that the report's first line names the prose hash and so clears `review owed` (REVIEW-OWED), and that the agent wrote only its one report. Independently read its findings and trace retellings. Keep an original failed reading in an isolated exercise when testing whether a reviewer trusts an explanation over the recorded trace.

For an existing project, run `node qualification/conformance/probe-project.ts <dossiers-root>`. It verifies without writes and checks each current component chart in memory. Exit 1 means findings or a chart that did not pass; it is not a reason to regenerate evidence automatically. Its stdout may contain project-specific identities, so retain it in local development records rather than this folder.

When a real repository exposes a defect, preserve the mechanism in a minimal synthetic fixture here and retain source provenance in the development records. Do not copy private knowledge records, addresses, machine paths or claims about deployed behavior into this directory.
